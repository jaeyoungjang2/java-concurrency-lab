쓰레드 풀의 한계
이제 쓰레드 풀을 미리 생성해놓고 작업을 할 수 있게 되었다.
오늘날 대부분의 웹 서비스는 요청 당 1개의 쓰레드를 할당한다.
요청이 들어오면 서블릿 컨테이너는 요청을 스레드 풀에 있는 하나의 스레드 풀에 할당한다.
쓰레드 풀을 많이 생성할 수록 속도가 빨라질까?
- 최대 쓰레드 수의 제한: 자바 쓰레드는 네이티브 스레드를 얇게 감싼 쓰레드, 즉 생성 가능한 최대 개수는 운영체제의 네이티브 스레드 최대 개수에 의해 제한된다.
- 메모리 사용량: 스레드가 힙 외부에서도 약 2Mib에 달하는 공간을 사용, 수천개의 동시 요청이 발생하면 메모리 사용량이 급증할 수 있다.
- 컨텍스트 전환 비용: 쓰레드 사이의 전환 즉 컨텍스트 전환 비용은 CPU 사이클을 소모하고, 이런 부분에서 성능 차이가 발생할 수 있다.

Executor의 한계
1. 캐시 일관성 유지 부하와 거짓 공유 위험
- CPU는 메인 메모리에서 데이터를 가져올 때 일반적으로 캐시 라인이라는 일정한 크기의 블록 단위로 가져옵니다.
- 캐시 라인의 크기는 CPU 아키텍처에 따라 다르지만, 일반적으로 64바이트가 많이 사용됩니다.
- CPU에는 L1, L2, L3 캐시가 있으며, 메인 메모리보다 빠르게 데이터에 접근하기 위해 사용합니다. 
- 멀티코어 환경에서는 각 코어가 캐시를 활용하기 때문에 데이터의 일관성을 유지해야 합니다. 이때 캐시 일관성 프로토콜을 통해 캐시 라인의 상태와 쓰기 소유권을 관리합니다. 
- 문제는 서로 다른 코어에서 서로 다른 변수를 수정하더라도, 해당 변수들이 동일한 캐시 라인에 위치할 수 있다는 것입니다. 
- 이 경우 한 코어가 데이터를 수정하면서 다른 코어의 캐시 라인을 무효화하고, 다른 코어가 다시 수정하기 위해 쓰기 소유권을 확보하는 과정이 반복될 수 있습니다. 
- 이렇게 실제로는 서로 다른 데이터를 수정하는데도 캐시 라인 단위의 일관성 관리 때문에 불필요한 성능 저하가 발생하는 현상을 **거짓 공유(False Sharing)**라고 합니다.
